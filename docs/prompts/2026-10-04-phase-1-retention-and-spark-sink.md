# Phase 1 retention and Spark sink follow-up prompt

현재 저장소의 로컬 보안 텔레메트리 파이프라인을 확인하고, 아래 보관·수집 목표를 반영하라.

먼저 저장소 전체 구조와 `AGENTS.md` 등 저장소 지침을 읽고, collector 수집 주기, 실제 이벤트 생성량, Kafka topic 설정, Spark Structured Streaming의 ClickHouse sink 구현, ClickHouse 테이블·TTL·볼륨 구성을 파악하라. 기존 코드와 데이터 의미를 확인한 뒤 변경하라. 관련 없는 사용자 변경은 수정하지 마라.

## 목표와 용량 가정

- Collector 수집 주기: 30초
- Kafka 보관 기간: 1일
- ClickHouse 원본 이벤트 보관 기간: 최근 7일
- ClickHouse 예상량: 7일간 약 210만 레코드
- Kafka 예상량: 1일간 약 30만 레코드

용량 목표는 고정된 레코드 수로 강제하지 말고, 실제 collector 이벤트 수에 따른 예상치로 취급하라. 위 수치는 평균 약 3.5 records/sec, 30초 수집 주기당 약 104 records에 해당하므로, 구현 후 실제 이벤트 수와 저장 크기를 측정해 가정을 검증하라.

## 작업 지시

1. **현재 용량과 저장량 확인**
   - 호스트의 사용 가능 디스크 공간과 Docker 데이터가 저장되는 볼륨 위치를 확인하라.
   - 실행 중인 서비스에 접근할 수 있다면 Kafka 데이터 크기와 ClickHouse 테이블 행 수·`system.parts`의 디스크 사용량을 확인하라.
   - 실제 이벤트 샘플 또는 기존 테이블 데이터에서 평균 serialized 크기와 ClickHouse 디스크상의 평균 크기를 측정하거나 추정하라.
   - 7일 예상 저장량과 merge 작업을 위한 여유 공간을 설명하라.
   - 실제 측정값 없이 저장 용량을 단정하지 마라. 디스크 부족 위험이 있으면 그 사실을 결과에 명확히 보고하라.

2. **Collector 수집 주기**
   - 기존 설정 방식을 따라 기본 수집 주기를 30초로 변경하라.
   - 환경변수나 설정 파일로 주기를 지정할 수 있다면 기본값과 문서를 함께 갱신하라.
   - 스케줄 작업이 겹쳐 중복 수집이나 무제한 대기가 발생하지 않는지 확인하라.
   - 프로세스·네트워크 상태를 매 주기 전체 스냅샷으로 반복 발행하는 구조라면, 기존 이벤트 의미와 범위 안에서 중복 이벤트를 줄일 수 있는지 먼저 검토하고 변경 내용을 설명하라. 요구된 보안 이벤트를 임의로 누락하지 마라.

3. **Kafka 보관**
   - 보안 이벤트 원본 topic의 보관을 1일(86,400,000ms)로 설정하라.
   - 해당 topic이 시간 기반 삭제를 사용하는지 확인하고, 압축 정책을 일반 메시지 압축과 혼동하지 마라.
   - 저유량 로컬 topic에서도 만료 데이터가 정리될 수 있도록 segment roll 및 실제 만료 동작을 확인하라. Kafka 정리는 세그먼트 단위이므로 1일이 초 단위의 정확한 삭제 시각을 뜻한다고 쓰지 마라.
   - 파티션별 용량 제한을 추가할 경우 파티션 수를 반영한 topic 전체 상한을 계산하고, 근거 없는 임의 용량값은 설정하지 마라.
   - Spark consumer가 1일 이상 중단되면 Kafka에서 재처리 가능한 데이터가 사라질 수 있다는 운영상 영향을 README 또는 실행 문서에 간결히 기록하라.

4. **ClickHouse 7일 보관**
   - 보안 원본 이벤트 테이블에 7일 TTL을 적용하라.
   - 보관 기준 timestamp는 기존 스키마의 `event_time`과 `collected_at` 의미를 비교해 선택하라. 수집 후 7일 보관을 보장하는 목적이라면 `collected_at` 사용을 우선 검토하고 선택 이유를 기록하라.
   - 기존 데이터가 있을 때 TTL 적용이 기존 7일 초과 데이터에도 영향을 주는지 설명하라. TTL 정리는 비동기일 수 있으므로 즉시 정확히 삭제된다고 보고하지 마라.
   - 이벤트 검색에 필요한 컬럼 구조를 유지하라. payload 전체를 압축 문자열 하나로 뭉쳐 쿼리 가능성을 없애지 마라.
   - 먼저 ClickHouse 기본 압축과 기존 MergeTree 설정을 확인하라. 별도 codec은 실측 이득이 있을 때만 적용하라.
   - 데이터 삭제를 위한 `TRUNCATE`, 테이블 재생성 또는 볼륨 삭제는 수행하지 마라. 7일 TTL을 통한 만료 동작으로 처리하라.

5. **Spark → ClickHouse 쓰기 단위 확인 및 수정**
   - Kafka 레코드가 Spark에서 ClickHouse까지 가는 실제 코드 경로를 추적하라.
   - ClickHouse에 대한 쿼리/insert 호출이 레코드별인지, Spark micro-batch별인지, Spark partition별인지 확인하고 근거가 되는 함수와 호출 위치를 보고하라.
   - 레코드마다 ClickHouse insert/query를 호출하는 구조라면, Spark DataFrame/Dataset 배치 sink를 사용해 micro-batch 또는 partition 단위로 여러 이벤트를 묶어 기록하도록 수정하라.
   - 이미 배치 방식이라면 불필요하게 다시 작성하지 말고 현재 배치 크기와 호출 단위를 검증하라.
   - 대량 데이터를 driver 메모리로 `collect()`하지 말고 Spark 분산 처리 구조를 유지하라.
   - micro-batch 재시도에 따른 중복 쓰기 가능성과 기존 checkpoint 동작을 점검하라. exactly-once를 보장하지 않으면 보장한다고 표현하지 마라.
   - 배치 insert 크기와 flush 주기를 로컬 처리량과 분석 지연의 균형에 맞춰 선택하고 근거를 기록하라.

6. **테스트 및 문서**
   - 30초 기본 주기 설정 테스트를 추가하라.
   - Kafka 1일 retention 설정을 확인하는 테스트 또는 설정 검증을 추가하라.
   - ClickHouse 7일 TTL 설정을 확인하라.
   - Spark sink가 레코드별 insert가 아닌 배치 단위 insert를 사용하는지 검증하는 테스트를 추가하라. 테스트가 실제 ClickHouse 없이 수행되는 경우 mock 또는 호출 계수로 insert 호출 단위를 검증하라.
   - 가능한 범위에서 end-to-end smoke test를 실행하고 수집 이벤트 수, Spark batch 처리 결과, ClickHouse 적재 행 수를 비교하라.
   - README에는 변경된 기본 수집 간격과 Kafka·ClickHouse 보관 기간, 알려진 데이터 손실 조건만 간단히 반영하라. 이후 단계의 기능을 추가하지 마라.
   - 실행한 검증과 실행하지 못한 검증을 분리해 최종 보고하라.
